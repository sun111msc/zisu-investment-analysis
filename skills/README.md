# Skills

这里的每份 `SKILL.md` 是一个**提示词接口**，不是一段提示词。

## 为什么单独一层

LLM 分析系统通常把指令直接写进代码字符串里，结果是：
指令无法单独评审、无法版本管理、无法测试、与代码逻辑纠缠。

本项目把「模型该怎么做」和「代码该怎么算」分成两层：

| 层 | 负责 | 位置 |
|---|---|---|
| **Skills** | 表达 —— 如何描述、如何论证、如何组织语言 | 本目录 |
| **Code** | 纪律与计算 —— 什么数据可用、什么结论可发、数字怎么算 | `src/zisu/` |

两层的边界很硬：**Skill 不能让越界的事发生**。
例如 Skill 里写「必须使用结构化数据源的估值倍数」，
这只是表达层的约定；真正让它生效的是 `GATE-01` 的登记门禁。
反过来，代码层也不会替模型写论证 —— 它只校验论证的**结构**是否完整
（有没有 ≥2 条非共识、空头强度是否够、有没有反事实）。

## 文件格式

每份 Skill 是一个 Markdown 文件，带 YAML frontmatter：

```markdown
---
name: skill-name
description: >
  何时应该加载这份 Skill。
---

# 标题
正文……
```

`name` 与目录名一致，`description` 写给**调度方**看 ——
它的作用是让调用方判断「这个任务该不该加载这份 Skill」。

## 调用协议

```
用户请求
   │
   ├─▶ 调度方读取各 Skill 的 description，决定加载哪些
   │
   ├─▶ 加载 deep-analysis（主流程）
   │       │
   │       └─▶ 同时加载 hard-enforcer（执行纪律）
   │
   ├─▶ 模型按 Skill 指引生成各阶段的自然语言产物
   │       │
   │       └─▶ 产物填入 Phase 定义的槽位（artifacts）
   │
   └─▶ 代码层执行闸门，产出三态
           │
           ├─ PASS           → 输出
           ├─ DRAFT_REVIEW   → 输出 + 强制状态声明
           └─ BLOCKED        → 只输出阻断原因清单
```

**关键约束**：Skill 不参与判定。模型生成的产物是否合格，
由闸门决定，不由 Skill 里的自我声明决定。

## 现有 Skill

| Skill | 角色 | 何时加载 |
|---|---|---|
| [`deep-analysis`](deep-analysis/SKILL.md) | 主流程指引 —— 八阶段各自该产出什么、深度要求是什么 | 执行完整分析时 |
| [`hard-enforcer`](hard-enforcer/SKILL.md) | 执行纪律 —— 不可跳过的清单与自检项 | 与主流程同时加载 |

## 新增 Skill 的约定

1. `description` 必须写清**触发条件**，不能只写「用于分析股票」
2. Skill 内不得出现具体数值结论（那是数据层的事）
3. Skill 内的每条要求，若属于「必须/禁止」级别，应能对应到某道闸门；
   对应不上的，说明它只是风格建议，需要在文中明确标注为「建议」而非「要求」
4. 不引用外部系统的本地路径
