# 0004. 输出采用三态而非二态

- 状态：已采纳
- 日期：2026-08-30
- 影响：中

## 背景

最初采用「成功 / 失败」二态。实践中发现，绝大多数情况落在两者之间：

- 系统跑完了，大部分检查通过，但某项数据超期了
- 估值算出来了，但反解不收敛
- 分业务拆解做了，但只有一条业务线（可能是真实情况，也可能是没拆）

二态会强迫做出坏选择：要么「假装通过」（放行有问题的报告），
要么「整份丢弃」（把 90% 可用的东西扔掉）。
两者都会导致使用者绕过系统 —— 一个总是拦人的系统会被关掉。

## 决策

采用三态：

| 状态 | 含义 | 能否输出结论 |
|---|---|---|
| `PASS` | 全部门禁通过 | ✅ 可作为正式结论 |
| `DRAFT_REVIEW` | 仅非阻断项失败 | ⚠️ 可输出，必须带状态声明，需人工复核 |
| `BLOCKED` | 任一阻断项失败 | ⛔ **不输出结论**，只输出阻断原因清单 |

配套设计：

1. **阻断性可配置**。每道闸门在登记时声明 `blocking`。
   时效超期是非阻断的（数据是旧的但仍可用），
   数据源越权是阻断的（数据可能完全错误）。
2. **状态声明必须出现在产出物里**。`GATE-40` 校验这一点。
3. **BLOCKED 时结论段物理缺失**，不是靠提示词要求模型不要输出。
   `StateDeclaration.can_emit_conclusion` 为假时，编排器不拼接报告正文。

## 备选方案

**方案 A：二态 + 警告列表。**
即「通过 + 一堆警告」。问题：警告会被忽略，因为它不影响结论。
三态的核心价值就是**让中间状态有名字**，有名字才会被处理。

**方案 B：连续评分（0-100）。**
更细腻，但阈值定在哪里都是任意的，
而且「73 分」比「需要复核」更不容易触发行动。

**方案 C：四态以上（加 `PARTIAL`、`STALE` 等）。**
状态越多，判定逻辑越复杂，实践中最容易被简化为
「是不是 BLOCKED」一个问题。三态是收益与复杂度的平衡点。

## 后果

**好处**：
- 系统不会因为一个小问题丢掉整份报告，也不会因为「大致没问题」放行严重错误
- `DRAFT_REVIEW` 这个中间态让「需要人工看一眼」变成显式流程
- 与阻断性配置结合后，可以精细控制哪些问题严重到必须停下

**代价**：
- 需要为每道闸门判断阻断性，判断错误会导致体验问题
- 使用者需要理解三种状态的区别（通过状态声明的文案缓解）

## 否决记录

**否决「用置信度分数代替状态」。** 试过输出「置信度 0.73」，
实测中使用者会把它当成概率做加权，而这并非它的含义。
状态是决策，分数是信息 —— 混淆两者会导致误用。

**否决「让模型输出状态」。** 状态由闸门结果程序化推导
（`resolve_state`），不由模型判断。模型倾向于输出 `PASS`。
