# 0002. 引入类型化数值契约

- 状态：已采纳
- 日期：2026-08-30
- 影响：高

## 背景

分析报告中出现过这类错误：

- 某分项占收入比重「0.898」被当作「89.8%」直接写进了正文，
  读者理解成 89.8 个百分点，实际是 89.8%。数字本身没错，口径错了。
- 引用了一个上一年度的估值倍数去解释当期股价，两者相差四个月，
  但报告里没有任何字段说明数据时点。
- 一份报告在流转五轮之后，其中一个关键数字的来源已经无法追溯，
  只能重做一遍核对。

共同点：**错误不在计算，而在口径。** 而且这类错误不会报错、
不会产生异常值，只是在结论层面安静地误导读者。

## 决策

引入 `TypedValue`，把数值包装成携带七属性的不可变对象：

```
value / unit / currency / frequency / semantic / as_of / source
```

三条配套规则：

1. **缺失必须显式**。`value=None` 时强制填写 `missing_reason`，
   且缺失值不参与任何算术运算（抛异常，而不是当 0）。
2. **量纲参与传播**。不同量纲相加直接报错；相除自动得到 `RATIO`；
   `RATIO → PERCENT` 需要显式调用 `to_percent()`。
3. **来源必须是已登记的数据源 ID**。与数据源登记门禁联动（见 ADR-0003），
   使得「无法溯源的数值」在结构上不可能出现。

## 备选方案

**方案 A：用带单位的字符串（如 `"100 亿元"`）。**
实现简单，但无法参与计算，且字符串比较极其容易出错。

**方案 B：用 `Decimal` + 文档约定单位。**
解决了浮点精度，但没有解决口径问题 —— 单位仍然只存在于文档里，
代码层面无法校验。

**方案 C：用现成的单位库（pint、astropy.units）。**
功能强，但引入运行时依赖，且金融语义（`pe_ttm` 是什么量纲？）
需要大量自定义，收益不抵成本。本项目的定位是零运行时依赖。

**方案 D：只加 `as_of` 和 `source` 两个字段，不管单位。**
成本最低，但挡住了三类错误中最常见的一类（单位混用），不可接受。

## 后果

**好处**：
- 单位混用在构造/运算时即暴露，不会流到结论
- 时效性可以程序化校验（`GATE-03`）
- 任何数值都能回答「来自哪里、什么时候的」
- 契约的七个字段本身就构成了一份数据字典

**代价**：
- 所有数值构造处都要提供七个字段，初期代码量增加约 30%
- 算术操作必须用 `add / sub / over / scale` 而非 `+ - * /`，
  写法不如原生运算自然
- 契约校验有一定开销（实测可忽略，因为数值量级在千级以下）

## 否决记录

**否决「用零值填充缺失」**。这是最容易实现、也最危险的做法：
零填不会报错，但它把一个缺失变成了一个错误的数值，
在后续所有计算中持续传播。改为强制显式缺失后，
`GATE-41` 可以反向检测出历史报告中的零填痕迹。

**否决「允许 `unit` 为空表示未知」**。曾考虑让量纲可选，
但实测中「未知量纲」很快会变成「懒得填」，
契约就失效了。现在单位是必填字段。
