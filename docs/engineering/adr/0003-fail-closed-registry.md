# 0003. 数据源采用编译期登记门禁

- 状态：已采纳
- 日期：2026-08-30
- 影响：高

## 背景

一次真实事故：分析过程中，模型为图省事，改用通用网页检索去估计一个
滚动市盈率。该数值与结构化数据库口径相比偏差 **+76% ~ +265%**。
而这个偏差直到人工复核才被发现 —— 因为系统没有任何机制检查它。

事故后复盘发现，提示词里其实明确写着「估值数据必须从数据库获取，
禁止用网页搜索替代」。也就是说，**约束是存在且清晰的，但没有生效**。

原因不在模型能力，而在**约束的性质**：提示词里的约束是「提醒」。
提醒可以被权衡（这次情况特殊）、被遗忘、被绕过。
一个可以自主决策的组件，面对提醒时的行为是不可靠的。

## 决策

把约束从「提示词提醒」上移为「**编译期登记门禁**」，分三级：

### 1. 登记制

任何数据源必须先在注册表中登记，声明其**能力边界**：

```python
DataSourceSpec(
    source_id="market.quote.primary",
    kind="market_data",
    allowed_semantics=frozenset({"price", "market_cap", "pe_ttm", ...}),
    priority=0,        # L0 主源
    ttl_days=1,
    structured=True,
)
```

### 2. 能力清单（CapabilityManifest）

分析开始**之前**，必须先声明本次将使用哪些源、各自覆盖哪些语义。
这是「先登记后使用」的落地形式。

### 3. 逐条核验

- **R001**：源未登记 → 阻断
- **R002**：源越权提供语义 → 阻断
  （典型：「新闻源」的 `allowed_semantics` 里**不含**任何估值语义，
  因此它在结构上就不可能提供 PE —— 不是「不许」，是「不能」）
- **R003**：必需语义无人承接 → 阻断

关键点：**默认拒绝，除非显式证明合规**（fail-closed）。

## 备选方案

**方案 A：强化提示词。** 加大字号、加感叹号、重复三次。
问题：仍然是提醒，无法验证是否被遵守。事故已经证明了这条路无效。

**方案 B：事后校验。** 分析完成后统一检查所有数值的来源。
问题：发现时已经算完，重做成本高；而且「来源」字段是由调用方填写的，
事后校验容易被绕过。

**方案 C：只允许硬编码的单一数据源。**
最安全，但牺牲了可用性 —— 数据源会挂，需要备源。

**方案 D：运行时白名单检查。**
在每次取数时检查源是否在白名单。比 A/B 好，但仍是运行时（分析已开始），
且没有利用「能力边界」这一层信息。

## 后果

**好处**：
- 未登记的源在计划阶段就被拒绝，**根本没有这条路径**
- 「新闻源不能提供估值数据」从文字纪律变成了类型约束
- 接入新数据源时被迫思考「它到底能提供什么」，这本身有价值
- 事故类型的错误在评测中可复现验证（见 `evals/injections.py` 的
  `unauthorized_source` 与 `unregistered_source` 两个注入）

**代价**：
- 接入新数据源多了一步登记，初期略繁琐
- 能力边界需要人工判定，判定错误会导致误拦（可通过放宽 `allowed_semantics` 修正）
- 注册表本身成为需要维护的资产

## 否决记录

**否决「先用了再补登记」**。曾考虑允许临时源在事后补登记，
但这等于给了一条绕过路径 —— 而绕过路径一定会被使用。
现在的要求是：**未登记 = 拒绝，没有例外。**

**否决「给闸门加全局跳过开关」**。调试时确实不方便，但一个
`--skip-gate-01` 参数在三个月后会出现在所有生产运行里。
需要放行时，修改规则本身（并更新本 ADR）。

**否决「把数据源绑定到具体供应商」**。注册表登记的是**逻辑源**
（`market.quote.primary` / `financials.statements.primary`），
而不是具体厂商。这样更换供应商不会动摇门禁规则。
