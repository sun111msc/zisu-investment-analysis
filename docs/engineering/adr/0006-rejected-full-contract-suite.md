# 0006. 否决全量工作簿契约体系

- 状态：已否决
- 日期：2026-08-30
- 影响：中

## 背景

在评估一个外部研究架构时，遇到一套「工作簿契约」设计：
把一次研究的全部中间产物声明为若干张结构化的表
（假设表、数据表、计算表、结论表……），每张表有固定列定义，
所有环节必须以「读表 / 写表」的方式交互，不允许直接传递对象。

这套设计在**多角色协作、需要交接**的场景下很有价值：
表格是显式的接口，任何人接手都能看懂前一步做了什么。

## 决策

**不采纳全量工作簿契约体系**，只吸收其中两项与执行治理相关的设计：
数据源登记门禁（→ ADR-0003）与三态输出（→ ADR-0004）。

## 否决理由

### 1. 与主估值锚冲突

本项目早期明确采用「单一主锚 + 交叉验证」的估值纪律，
而工作簿契约要求每个环节输出结构化的中间表，
估值会退化为「多个表之间的算术」，主锚的判定逻辑被稀释。
（后续该纪律本身也演进为多锚交叉，见 `GATE-51`，
但那是通过显式的锚登记实现的，不是通过表格契约。）

### 2. 工程成本远超收益

全量契约意味着：

- 二十余个模块，每个模块的表结构需要定义、版本管理、迁移
- 任何中间结论的改动都要同步改表定义
- 单机单人使用时，这些表几乎不会被单独阅读

在**单人研究**的场景下，表格契约的主要价值（交接清晰）不存在，
而成本（维护开销）全额承担。

### 3. 与「阶段只通过 artifacts 通信」重复

本项目已经有类似的机制：阶段之间只通过 `artifacts` 字典通信，
不互相引用对象（见 `pipeline/base.py` 的约定）。
这提供了同样的解耦效果，但结构更轻 ——
新增一个产物只需在 `Phase.provides` 里加一个键。

### 4. 契约应该用在错误代价高的地方

全量契约的思路是「处处设防」。但工程判断力体现在**选择性**：
把契约用在高价值位置（数值、数据源），其他地方保持灵活。

本项目的契约只加在三处：

- 数值入口（`TypedValue`）
- 数据源边界（`DataSourceSpec`）
- 阶段接口（`provides` / `requires`）

这三处覆盖了绝大多数严重错误的来源，其余环节不做结构化约束。

## 采纳的部分

| 设计 | 采纳方式 |
|---|---|
| 数据源编译期登记 | 完整采纳，见 ADR-0003 |
| 三态输出（PASS / DRAFT_REVIEW / BLOCKED） | 完整采纳，见 ADR-0004 |
| 类型化数值属性 | 借鉴其思路，扩展为七属性，见 ADR-0002 |
| 全量工作簿契约 | **否决** |
| 二十余模块表结构 | **否决** |

## 后果

**好处**：
- 系统复杂度可控，`src/` 下不到 20 个模块
- 新增能力不需要同步修改多处表定义
- 注意力集中在对错误影响最大的三处契约上

**代价**：
- 中间产物缺少统一的结构化定义，跨阶段复用依赖约定
  （通过 `Phase.provides` 声明缓解）
- 如果未来需要多人协作，可能需要重新评估这一决定

## 说明

本 ADR 存在的意义不在于结论本身，而在于**记录「否决了什么、为什么」**。

一个只有采纳记录、没有否决记录的仓库，通常意味着
没有认真比较过备选方案 —— 而这比选错更难被察觉。
