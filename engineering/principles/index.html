    设计原则¶

    本项目的每一条原则都来自一次具体的失败，而不是先验的美学偏好。 原则以「可被违反的约束」形式表述 —— 无法被证伪的原则没有意义。

    一、数据必须先登记，再使用¶

    约束：任何进入分析链路的数据源，必须先在注册表中登记其能力边界。

    违反的表现：用通用网页检索去获取估值倍数，口径与结构化数据库相差 +76% ~ +265%。

    为什么提示词不够：写在提示词里的约束依赖模型自觉，而模型会权衡、 会认为「这次不一样」、会遗忘。写在代码里的约束不依赖任何人的自觉。

    实现：datasources/registry.py → GATE-01

    二、缺失是合法状态，零值不是¶

    约束：查不到的数据必须显式标记为缺失并说明原因，禁止用 0 填充。

    违反的表现：应收账款查不到就填 0，于是「应收账款周转天数」算出来是 0 天， 看起来是极佳的经营效率，实际上是数据缺失。

    为什么危险：零值填充不会报错、不会警告，它只是安静地把一个缺失 变成一个错误的数字。这类错误在结论层面几乎无法被发现。

    实现：contracts/value.py → TypedValue.missing()、GATE-41

    三、每个数字都要能回答「你从哪来、什么时候的」¶

    约束：数值必须携带时点与来源，缺少任一项即为契约违反。

    违反的表现：报告里写「当前 PE 22 倍」，但没有说明这是哪天的、 数据来自哪里。三个月后回看，只能重做一遍。

    实现：contracts/value.py 七属性 → GATE-02、GATE-03、GATE-42

    四、业务事实先于市场认知¶

    约束：先建立独立的业务理解，再讨论市场共识；讨论市场时只提问、不给结论。

    违反的表现：先写「市场认为该公司是XX」，然后整篇分析都围绕这个判断 去找证据 —— 这是循环论证，且很难自我察觉。

    实现：流水线 P0-P3 早于 P4；穿透铁律一只适用于 P4

    五、结论必须可证伪¶

    约束：核心论点必须能写成一个可以被事实推翻的句子，并配可观测的验证指标。

    违反的表现：「行业景气度提升，公司有望受益」—— 这句话无法被任何 数据推翻，因此它不构成一个观点，只是一个姿态。

    实现：GATE-23 反事实推理要求 if / then / observable 三要素齐全

    六、空头论证必须不弱于多头¶

    约束：魔鬼代言人的高证据等级论据数量不得少于多头。

    违反的表现：空头章节写三条「估值偏高」「竞争加剧」之类的通用风险， 多头章节写五条带证据的论据。表面上做了风险提示，实际上是自我确认。

    实现：GATE-16

    七、反向提问优先于正向预测¶

    约束：估值环节必须执行反向 DCF，反解市场隐含预期；反向 DCF 不产出目标价。

    违反的表现：给出一个精确到小数点后两位的目标价，而其中 70% 来自 对永续增长率的假设 —— 这是把自己的假设包装成客观结论。

    实现：valuation/reverse_dcf.py、GATE-50；接口层面不提供价格字段

    八、失败要关闭，不要降级通过¶

    约束：闸门失败即失败，不提供全局跳过的开关；需要放行时修改规则本身并记录 ADR。

    违反的表现：给闸门加一个 --skip-gates 参数「方便调试」， 三个月后所有生产运行都带着这个参数。

    实现：GateEngine.run() 无 skip 参数；规则异常按阻断处理

    九、单一锚不构成结论¶

    约束：估值必须至少两个锚交叉，且离散度不得超过 80%。

    违反的表现：只用一个 PE 倍数得出结论，而不同方法给出的估值相差两倍以上 却只报告其中一个。

    实现：GATE-51

    十、文档与代码同源¶

    约束：docs/engineering/gate-catalog.md 中的闸门编号必须与代码一致，CI 会校验。

    违反的表现：文档说 56 道闸门，代码只有 25 道；文档说 v8.0，代码是 v6.6。 文档漂移会让整个项目的可信度失效 —— 读者无法判断哪份才是真的。

    实现：.github/workflows/ci.yml 中的一致性检查步骤
