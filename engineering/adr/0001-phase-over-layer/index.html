    0001. 用 Phase 取代 Layer 作为主编号体系¶

    • 状态：已采纳
    • 日期：2026-07-22
    • 影响：高

    背景¶

    早期版本用「层」（Layer）组织流程：从环境评估、数据采集、瓶颈分析、 多维印证一路到风控执行，共十几层，编号里还有 0.15、0.25、1.5、2.5 这样的半层。

    这套编号在系统演进中出现三个问题：

    1. 语义混淆。「层」既表示执行顺序，又表示抽象层次，还表示模块归属。 说「第 3 层」时，听的人不知道指的是第三步还是第三个抽象级别。

    2. 半层爆炸。每当需要插入一个新环节，就往编号里塞一个 .5。 最后出现 0.15、0.25、0.5b 这类编号，新人无法理解执行顺序。

    3. 与时间尺度冲突。资金行为层（Layer 2.5）既参与数据采集，又参与风险评估， 单一编号无法表达它被用在两个不同时点。

    决策¶

    改用 Phase（阶段） 作为唯一主编号体系，八阶段，编号连续无小数：

    P0 公司画像 → P1 行业定位 → P2 深度穿透 → P3 财务预测
→ P4 市场认知 → P5 估值定价 → P6 执行方案 → P7 最终裁决

    「层」的语义降级为执行时点标注：某个计算环节属于哪个 Phase、 在什么条件下被触发，写在 Phase 的说明里，不再参与编号。

    同时把原编号体系重新排序，让分析顺序与认知顺序一致（见 0002 之外的 「正金字塔」重构）：业务事实先行，市场认知后置。

    备选方案¶

    方案 A：保留 Layer，只清理半层。 把 0.15/0.25 合并进相邻整数层。问题：没有解决语义混淆， 「层」的歧义仍然存在，且插入新环节时仍会退化。

    方案 B：改用 DAG 节点编号。 按依赖关系给节点编号。问题：读者需要先理解依赖图才能读流程， 可读性反而下降；而且实际流程是近似线性的，DAG 是过度设计。

    方案 C：不编号，用名称。 可读性最好，但无法在代码和文档中引用，评审时无法精确定位。

    后果¶

    好处： - 编号与执行顺序一一对应，无歧义 - 新增环节只需调整 Phase 内部，不破坏全局编号 - 文档、代码、测试可以用同一套编号互相引用

    代价： - 历史文档中的 Layer 编号全部失效，需要迁移（一次性成本） - 已经按 Layer 编号写成的检查清单需要重排

    否决记录¶

    否决「同时保留两套编号」。曾考虑保留 Layer 作为辅助索引， 但两套编号并存会导致文档中混用（实测中确实出现了同一个文件里 同时使用 §L-1、Layer 2.5、Phase 2-5 三种编号的情况）， 这比只有一套编号更糟。编号体系必须唯一，旧体系只在迁移说明中出现。
